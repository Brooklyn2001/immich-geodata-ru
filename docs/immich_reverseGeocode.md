# Принцип работы обратного геокодирования в Immich и подход к русской локализации

**🇷🇺 Русский** | [🇬🇧 English](immich_reverseGeocode_EN.md)

По умолчанию Immich определяет местоположение фотографий довольно странно: не только на английском, но и с использованием необычных названий. Это создаёт большие неудобства при сортировке и поиске фотографий. В выходные я подробно изучил, как именно Immich реализует обратное геокодирование, и попытался его локализовать. Если вы здесь для того, чтобы реализовать локализацию названий мест, сразу переходите [к этому проекту](https://github.com/Brooklyn2001/immich-geodata-ru).

## Как работает обратное геокодирование в Immich

Чтобы достичь цели локализации, сначала нужно понять, как Immich выполняет обратное геокодирование локально.

### Обратное кодирование

Рассмотрим на примере v1.124.2. Обратное геокодирование в Immich реализовано в функции [`reverseGeocode`](https://github.com/immich-app/immich/blob/1311189fab958bea2177a92e1cc1b7ebb1822bd8/server/src/repositories/map.repository.ts#L108). На вход подаётся объект `GeoPoint`, который по сути представляет собой долготу и широту. Затем по этим координатам выполняется следующий SQL-запрос:

```sql
SELECT * FROM geodata_places
WHERE earth_box(ll_to_earth_public(${point.latitude}, ${point.longitude}), 25000) @> ll_to_earth_public(latitude, longitude)
ORDER BY earth_distance(ll_to_earth_public(${point.latitude}, ${point.longitude}), ll_to_earth_public(latitude, longitude))
LIMIT 1;
```

Здесь:
- `earth_box` создаёт сферическую область с центром в заданной точке.
- `ll_to_earth_public` преобразует географические координаты (широту и долготу) в точку на трёхмерной сфере.
- Условие `WHERE` отбирает географические точки, находящиеся в пределах 25 000 метров (25 км) от входной точки.
- `ORDER BY` сортирует их по расстоянию от ближайшей к дальней.

Иными словами, находится ближайшая географическая точка в таблице `geodata_places` к входной точке. После нахождения ближайшей точки из неё извлекаются `{ countryCode, name: city, admin1Name }` — код страны, название и название административной единицы первого уровня. Затем порядок приводится в соответствие, а код страны преобразуется в название страны. Это соответствует трём уровням местоположения фотографии в Immich: **страна, провинция, город**.

Название и название административной единицы первого уровня берутся напрямую из таблицы базы данных, а название страны получается из кода страны с помощью метода `getName` библиотеки [`node-i18n-iso-countries`](https://github.com/michaelwittig/node-i18n-iso-countries). Однако в коде Immich вызов выглядит как `getName(countryCode, 'en')` — язык жёстко задан как `'en'`, поэтому результат всегда на английском, и никакого механизма i18n не предусмотрено.

Если вышеуказанный поиск не дал результатов, выполняется ещё один SQL-запрос:

```sql
SELECT * FROM naturalearth_countries
WHERE coordinates @> point(:longitude, :latitude)
LIMIT 1;
```

Этот запрос ищет в таблице `naturalearth_countries` записи, чьи координаты содержат входные координаты, то есть определяет страну по разграничению стран в наборе данных Natural Earth. Если используется этот путь, более детальное определение провинции и города уже не производится.

Короче говоря, Immich заранее подготавливает в базе данных множество географических названий, затем сопоставляет координаты фотографии с ближайшим названием в базе и использует его в качестве названия места. Если найти не удаётся, происходит откат к использованию только информации о стране на основе её административного деления.

### Построение данных

Следующий важный вопрос: откуда берутся данные в базе? Все данные обратного геокодирования Immich поступают из [GeoNames](https://www.geonames.org/) и размещаются в папке `/build/geodata`. При каждом выпуске версии оттуда [загружаются](https://download.geonames.org/export/dump/) самые свежие данные.

В папке находятся следующие файлы:
- `admin1CodesASCII.txt`: список административных единиц первого уровня (id | name | name ascii | geoname id)
- `admin2Codes.txt`: список административных единиц второго уровня (id | name | name ascii | geoname id)
- `cities500.txt`: список всех городов с населением более 500 человек
- `geodata-date.txt`: дата обновления данных
- `ne_10m_admin_0_countries.geojson`: разграничение стран Natural Earth, подробнее можно [посмотреть здесь](https://github.com/nvkelso/natural-earth-vector/tree/master)

Точка входа для импорта — функция [`init`](https://github.com/immich-app/immich/blob/1311189fab958bea2177a92e1cc1b7ebb1822bd8/server/src/repositories/map.repository.ts#L41C1-L42C1). Сначала она проверяет значение `reverse-geocoding-state` в `system-metadata`, где хранится время `lastUpdate` — время последнего импорта данных. Это время сравнивается со временем в файле `geodata-date.txt`. Если время в файле новее, значит, есть обновлённые данные, и начинается импорт; в противном случае он пропускается во избежание повторного импорта.

Логика импорта находится в [`importGeodata`](https://github.com/immich-app/immich/blob/1311189fab958bea2177a92e1cc1b7ebb1822bd8/server/src/repositories/map.repository.ts#L207). Помимо логики создания таблиц, ключевым является функция [`loadCities500`](https://github.com/immich-app/immich/blob/1311189fab958bea2177a92e1cc1b7ebb1822bd8/server/src/repositories/map.repository.ts#L226C3-L226C11). Файл `cities500.txt` имеет формат, похожий на CSV, с разделителем `\t`. Преобразование в содержимое базы данных происходит по следующим правилам:

```javascript
id: Number.parseInt(lineSplit[0]),
name: lineSplit[1],
alternateNames: lineSplit[3],
latitude: Number.parseFloat(lineSplit[4]),
longitude: Number.parseFloat(lineSplit[5]),
countryCode: lineSplit[8],
admin1Code: lineSplit[10],
admin2Code: lineSplit[11],
modificationDate: lineSplit[18],
admin1Name: admin1Map.get(`${lineSplit[8]}.${lineSplit[10]}`) ?? null,
admin2Name: admin2Map.get(`${lineSplit[8]}.${lineSplit[10]}.${lineSplit[11]}`) ?? null,
```

Здесь `admin1Map` и `admin2Map` — это отображения из id в name, полученные путём чтения файлов `admin1CodesASCII.txt` и `admin2Codes.txt`.

В сочетании с логикой обратного кодирования, описанной выше, это означает, что по широте и долготе находится ближайшая точка, затем берутся её `countryCode`, `admin1Name` и `name` — эта информация и становится географическим местоположением фотографии.

Верно, `admin2Name` вообще не используется, и `admin2Codes.txt` тоже не задействован.

## Подход к локализации

Immich разделяет географическую информацию о фотографии на три уровня: **страна, провинция, город**. Ещё раз обобщим роли файлов:
- Из `cities500.txt` находится ближайшая точка, её название берётся как **город**.
- По информации `admin1Code` этой точки в файле `admin1CodesASCII.txt` находится название уровня **провинции**.
- По `countryCode` этой точки с помощью [`node-i18n-iso-countries`](https://github.com/michaelwittig/node-i18n-iso-countries) получается название уровня **страны**.

Теперь, когда роли ясны, подход к локализации становится очевидным.

### Страна

Этот шаг в основном зависит от библиотеки [`node-i18n-iso-countries`](https://github.com/michaelwittig/node-i18n-iso-countries), а в [коде](https://github.com/immich-app/immich/blob/1311189fab958bea2177a92e1cc1b7ebb1822bd8/server/src/repositories/map.repository.ts#L131) целевой язык преобразования жёстко задан как `en`. Изменить целевой язык невозможно, поэтому остаётся работать с данными этой библиотеки. Данные библиотеки также реализованы в виде статических файлов, содержимое которых можно посмотреть [здесь](https://github.com/michaelwittig/node-i18n-iso-countries/tree/master/langs). Файл `en.json` — это источник данных для преобразования в `'en'`. Нам достаточно переписать его на русский, а русская информация находится в `ru.json`. Нужно просто заменить файл, как показано [здесь](https://github.com/Brooklyn2001/immich-geodata-ru/blob/main/i18n-iso-countries/langs/en.json). В итоге остаётся заменить изменённый файл на оригинальный в образе Immich.

### Провинция

Названия провинций находятся в файле `admin1CodesASCII.txt`. К счастью, [GeoNames](https://download.geonames.org/export/dump/) предоставляет файл `alternateNamesV2.zip`, содержащий названия многих мест на разных языках. С помощью этой информации можно напрямую выполнить перевод, заменив исходные названия. Реализация кода находится [здесь](https://github.com/Brooklyn2001/immich-geodata-ru/blob/main/geodata/translate.py#L119).

### Город

Основная цель для файла `cities500.txt` — перевести поле `name`. Однако при изучении этого файла можно заметить, что его детализация очень высока: он включает не только города, но и районы, уезды, а также очень старые названия, что делает его малопригодным для использования. Чтобы решить эту проблему, можно повторно идентифицировать эти места через API обратного геокодирования и получить стандартные названия административных единиц первого и второго уровня. Здесь реализована версия для [использования Nominatim](https://github.com/Brooklyn2001/immich-geodata-ru/blob/main/geodata/generate_geodata_nominatim.py) (с `accept-language: ru`).

Кроме того, из-за ограниченного объёма данных в стандартном файле `cities500.txt` в некоторых регионах может быть мало точек, что приводит к ошибкам при обратном геокодировании в Immich. На самом деле [GeoNames](https://download.geonames.org/export/dump/) также предоставляет полную информацию о географических точках по странам, например `RU.zip`, которую можно добавить в `cities500.txt` в качестве дополнения для повышения качества. Реализация находится [здесь](https://github.com/Brooklyn2001/immich-geodata-ru/blob/main/geodata/enhance_data.py). Однако, учитывая огромный объём данных, по умолчанию добавлены только крупные города; при необходимости можно добавить и другие.
